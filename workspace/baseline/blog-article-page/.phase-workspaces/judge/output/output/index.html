Why We Migrated From REST to GraphQL

By Priya Sharma on November 12, 2025

After five years of building APIs with REST, our team at DataFlow decided it was time for a fundamental shift. This article details our journey from traditional REST endpoints to GraphQL, the challenges we faced, and the surprising benefits we discovered along the way.

The Problem

Our REST API had grown into a sprawling collection of endpoints. The mobile app needed different data shapes than the web application, and each client had to request multiple endpoints to assemble complete information. This led to what we call "endpoint multiplication" — we found ourselves maintaining over 150 different endpoints, many of them variations created specifically for individual client needs.

Over-fetching was another significant problem. When the web frontend needed just a user's name and email, it had to download their entire user profile, including account settings, preferences, and billing information. This was particularly painful for mobile users on slower connections.

The lack of a unified schema meant that documentation was scattered across Swagger specs, outdated wiki pages, and tribal knowledge. Onboarding new engineers became increasingly difficult.

Our Approach

We chose to implement Apollo Server as our GraphQL engine, running alongside our existing REST API. Rather than a big-bang rewrite, we took a gradual migration approach, moving one service at a time to the new GraphQL layer.

Our strategy included:

  • Building a federated schema using Apollo Federation to organize our graph across teams
  • Creating a caching layer with Redis to handle the increased query complexity
  • Implementing query depth limiting and cost analysis to prevent abuse
  • Establishing clear naming conventions and style guidelines for our schema

The first service we migrated was our user service, which was relatively straightforward. We exposed a set of GraphQL types (User, Profile, Preferences) and verified that our primary web client could function with the new API. Here's a simplified example of what this query looked like: 

query GetUserProfile($userId: ID!) {
  user(id: $userId) {
    id
    name
    email
    profile {
      bio
      avatarUrl
    }
    preferences {
      theme
      notifications {
        email
        push
      }
    }
  }
}

This single query replaced what previously required four separate REST API calls. The client could request exactly the fields it needed, nothing more, nothing less.

Results

After twelve months of migration work, we successfully moved 80% of our API surface to GraphQL. The results exceeded our expectations:

  • Reduced API calls: The web frontend went from an average of 45 API calls per page load to 8, with improvements in both perceived and actual performance
  • Smaller payloads: Average response payload size decreased by 65% due to precise field selection
  • Faster development: Time to implement new client features decreased by 40%, largely because the schema was self-documenting and introspectable
  • Better mobile experience: Mobile app data usage dropped by 58%, translating to improved battery life and reduced bandwidth costs
  • Unified documentation: The GraphQL schema became the source of truth, automatically documented through introspection

Perhaps most importantly, our engineering team felt more productive and happy. The developer experience with GraphQL tools like Apollo DevTools and GraphiQL made debugging and development significantly easier.
